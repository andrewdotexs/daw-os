# P0.1 — Ambiente di sviluppo su WSL2

- **Macchina**: PC di sviluppo (Windows 11 con WSL2). Il 285K non è coinvolto.
- **Stato**: **superato** il 13 novembre 2026 (`RESULT: PASS`, un avviso sulla memoria; vedi «Esito»).
- **Accettazione**: `make check-env` termina con `RESULT: PASS`.

## Cosa fa questo passo

Prepara il PC di sviluppo a costruire l'immagine con Buildroot e ad avviarla in QEMU. Non costruisce ancora nulla: verifica soltanto che, quando lo faremo, non ci siano sorprese.

## File consegnati

| File | Scopo |
| --- | --- |
| `tools/check-env.sh` | Verifica l'ambiente e stampa una riga per controllo. È il criterio di accettazione. |
| `Makefile` (bersaglio `check-env`) | Richiama lo script. |

I due file di configurazione di WSL non stanno nel repository, perché appartengono alla tua macchina: sono riportati qui sotto.

## Scelte tecniche

**Repository dentro il file system di Linux.** I dischi di Windows visti da WSL2 (`/mnt/c`) passano per un protocollo di rete interno: sono lenti di un ordine di grandezza e non distinguono maiuscole da minuscole, il che rompe la costruzione del kernel. Tutto il lavoro sta sotto la tua cartella personale in WSL.

**`PATH` senza i percorsi di Windows.** Per impostazione predefinita WSL aggiunge al `PATH` le cartelle di Windows, che contengono spazi (`Program Files`). Buildroot rifiuta di partire con un `PATH` che contiene spazi. Si disattiva con `appendWindowsPath=false`. L'effetto collaterale è che i programmi di Windows non si richiamano più per nome dalla shell di WSL; si possono ancora richiamare con il percorso completo.

**systemd dentro WSL.** Non è indispensabile per Buildroot, ma rende normali i servizi (per esempio il server HTTP degli aggiornamenti, più avanti) e i gruppi dei dispositivi.

**Virtualizzazione annidata.** QEMU con KVM avvia l'immagine in pochi secondi; senza KVM emula il processore ed è 20–50 volte più lento. WSL2 è già una macchina virtuale, quindi KVM richiede la virtualizzazione annidata, che Windows 11 supporta.

**Permessi di `/dev/kvm`.** In WSL2 il dispositivo nasce spesso accessibile solo a root. Il comando di avvio in `wsl.conf` lo assegna al gruppo `kvm`, a cui si aggiunge il tuo utente.

**Dimensionamento.** WSL2 prende per impostazione predefinita metà della RAM e tutti i processori. La costruzione usa tutti i core che trova e circa 1 GiB per lavoro di compilazione nei momenti peggiori _(stima)_. Il PC di sviluppo ha 8 core e 16 GB: a WSL vanno 12 GB e tutti i core, cioè 9 lavori paralleli con più di 1 GiB ciascuno. La memoria di WSL è dinamica: i 12 GB sono un tetto, non una prenotazione.

**Ubuntu 24.04.** È la distribuzione su cui ho provato script e costruzione. Un'altra distribuzione funziona, ma cambiano i nomi dei pacchetti e i percorsi di OVMF; lo script di avvio in QEMU conosce già quelli di Fedora e Arch.

## Comandi

### 1. Su Windows, in PowerShell

Installare o aggiornare WSL e la distribuzione:

```powershell
wsl --update
```

```powershell
wsl --install -d Ubuntu-24.04
```

```powershell
wsl --version
```

Mi aspetto: una versione di WSL 2.x e un kernel 5.15 o 6.x. Annotala.

Creare il file `%UserProfile%\.wslconfig` con questo contenuto, dimensionato sul PC di sviluppo (8 core, 16 GB).

```ini
[wsl2]
# Needed for /dev/kvm inside WSL2 (QEMU with KVM acceleration).
nestedVirtualization=true
# Ceiling for the WSL2 virtual machine: 16 GB installed, 4 GB left to Windows.
memory=12GB
# No "processors" line: WSL2 uses all 8 cores.
# Swap absorbs the peaks of the link steps; it lives on the Windows disk.
swap=8GB
```

Applicare la configurazione riavviando WSL:

```powershell
wsl --shutdown
```

### 2. Dentro WSL, la prima volta

Creare `/etc/wsl.conf`:

```bash
sudo tee /etc/wsl.conf > /dev/null <<'EOF'
[boot]
systemd=true
# /dev/kvm is created root-only: hand it to the kvm group at every start.
command = /bin/sh -c 'chown root:kvm /dev/kvm && chmod 660 /dev/kvm'

[interop]
# Keep Windows directories (with spaces) out of PATH: Buildroot refuses them.
appendWindowsPath=false
EOF
```

Installare i pacchetti:

```bash
sudo apt update
```

```bash
sudo apt install -y build-essential git rsync bc cpio unzip file wget python3 \
  libncurses-dev libssl-dev libelf-dev \
  qemu-system-x86 ovmf shellcheck npm
```

Aggiungere il tuo utente al gruppo `kvm`:

```bash
sudo usermod -aG kvm "$USER"
```

Tornare in PowerShell e riavviare WSL perché `wsl.conf` e il gruppo abbiano effetto:

```powershell
wsl --shutdown
```

### 3. Dentro WSL, clonare il repository

Nella cartella personale, **non** sotto `/mnt/c`. Il lavoro è sul ramo `claude/affectionate-faraday-5le4g4`.

```bash
cd ~ && git clone --recurse-submodules -b claude/affectionate-faraday-5le4g4 \
  https://github.com/andrewdotexs/daw-os.git
```

```bash
cd ~/daw-os
```

Se il repository era già clonato senza sottomoduli:

```bash
git submodule update --init
```

### 4. Verifica

```bash
make check-env
```

Mi aspetto esattamente questa forma, con i tuoi numeri nelle ultime due righe:

```text

  OK    repository is on the Linux filesystem (/home/<utente>/daw-os)
```

## Esito

Eseguito sul PC di sviluppo il 13 novembre 2026: tutti i controlli `OK`, compresi `/dev/kvm` e il sottomodulo al tag atteso. Un solo avviso:

```text
WARN  7 GiB of RAM visible: builds may be slow or run out of memory (see .wslconfig)
```

Il passo è superato. L'avviso si spiega con i dati del PC, arrivati dopo: 16 GB installati e nessun valore di `memory` attivo, quindi WSL prendeva la metà predefinita.

### Il PC di sviluppo

| Voce | Valore | Conseguenza |
| --- | --- | --- |
| Processore | Intel Core Ultra 7 256V: 4 P-core e 4 E-core, 8 thread | 9 lavori di compilazione; prima costruzione stimata in 20–30 minuti _(stima)_. |
| RAM | 16 GB, saldata | `memory=12GB` per WSL, 4 GB a Windows. |
| Disco | NVMe da 954 GB, 406 GB liberi | Sufficiente; vedi la nota sullo spazio. |
| Sistema | Windows 11 Home, versione 26H2 | Virtualizzazione annidata funzionante (`/dev/kvm` utilizzabile). La rete in modalità speculare, che serve dal passo P0.5, è da provare sull'edizione Home. |
| Distribuzione | Ubuntu 24.04, installata con questa guida | Quella su cui gli script sono stati provati. |
| WSL | Versione 3.0.5, kernel 6.18.58, Windows build 26300 | Versione recente: il comando di avvio in `wsl.conf` e la virtualizzazione annidata funzionano, come conferma `/dev/kvm`. |
| Rete | Stessa rete cablata del 285K; il 285K ha un indirizzo fisso; nessun firewall o antivirus di terze parti | Aggiornamenti via HTTP sulla rete locale praticabili (P0.5). |
| Chiavetta USB | Disponibile | Prima installazione sul 285K (P0.4). |
| Uso durante le costruzioni | Tutti i core disponibili | Nessun limite a `processors`. |

### Nota sullo spazio

`make check-env` aveva riportato 954 GiB liberi: è la dimensione massima del disco virtuale di WSL, non lo spazio reale. Il disco virtuale cresce sul disco di Windows, dove i GiB liberi sono 406. Lo script ora controlla anche quello, quando gira in WSL.

### Memoria e lavori paralleli

Buildroot compila con un lavoro in più dei processori che vede, qui 9. Ogni lavoro, nei momenti peggiori, occupa circa 1 GiB _(stima, non misura)_. Se i lavori sono più dei GiB disponibili, il kernel di Linux può terminare un compilatore per mancanza di memoria e la costruzione fallisce con un errore poco chiaro (`Killed`, `internal compiler error`).

Con il `.wslconfig` della sezione «Comandi» (`memory=12GB`, `swap=8GB`) WSL vede circa 11 GiB: bastano per i 9 lavori. Dopo averlo scritto:

```powershell
wsl --shutdown
```

Poi `make check-env` deve terminare con `RESULT: PASS (0 warnings)`.

Se in futuro la memoria tornasse scarsa, per esempio con altri programmi aperti, la variabile `JOBS` limita i lavori paralleli, e `make check-env` suggerisce il valore:

```bash
make image JOBS=6
```

Durante la costruzione Windows resta con 4 GB: conviene chiudere i programmi pesanti.

## Se qualcosa fallisce

| Riga | Causa probabile | Rimedio |
| --- | --- | --- |
| `FAIL  PATH contains whitespace` | `wsl.conf` non applicato | Controllare il file e ripetere `wsl --shutdown`. |
| `FAIL  /dev/kvm missing` | Virtualizzazione annidata non attiva, o virtualizzazione disattivata nel firmware del PC | Controllare `.wslconfig`; nel firmware attivare VT-x o SVM. |
| `FAIL  /dev/kvm exists but is not accessible` | Gruppo `kvm` non ancora attivo | `wsl --shutdown`, poi `id` deve elencare `kvm`. |
| `FAIL  repository is on a Windows drive` | Clonato sotto `/mnt/c` | Clonare di nuovo sotto `~`. |
| `FAIL  Buildroot submodule …` | Sottomodulo non scaricato | `git submodule update --init`. |
| `FAIL  <N> GiB free` | Disco virtuale di WSL piccolo o pieno | Vedi la nota sotto. |
| `WARN  <N> GiB of RAM for <M> CPUs` | Meno di 1 GiB per lavoro di compilazione | Usare il valore di `JOBS` indicato, o alzare `memory` in `.wslconfig`. |
| `FAIL  <N> GiB of RAM visible` | Meno di 4 GiB | Alzare `memory` in `.wslconfig`. |

Il disco virtuale di WSL cresce da solo fino a un massimo (1 TB nelle versioni recenti), ma occupa spazio reale sul disco di Windows dove risiede: servono almeno 40 GiB liberi lì.

## Da verificare sulla tua macchina

Non ho potuto provare questo passo su Windows: l'ho provato su Ubuntu 24.04 nativo, dove lo script segnala correttamente l'assenza di KVM e lo spazio insufficiente. Restano da confermare da te:

- che `nestedVirtualization=true` basti a far comparire `/dev/kvm` sulla tua versione di Windows e di WSL;
- che il comando in `[boot]` di `wsl.conf` venga eseguito (richiede una versione recente di WSL) e che `/dev/kvm` risulti `root:kvm` con permessi `660`;
- che `appendWindowsPath=false` non ti tolga strumenti di Windows che usi dalla shell di WSL.
