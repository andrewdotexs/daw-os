# P0.5f — Installazione sul 285K e prove finali del passo P0.5

- **Macchine**: PC di sviluppo e 285K.
- **Prerequisito**: P0.5e superato.
- **Stato**: in corso sul 285K dal 15 novembre 2026 (immagine `0.0.1.20261115113440`; sul PC di sviluppo `make qemu-test` `PASS` con `timers=none`). Consegnato: Tutto ciò che si può provare senza il 285K l'ho provato in QEMU; il resto è elencato in «Da verificare sul 285K».
- **Accettazione**: il 285K, installato dalla chiavetta **per l'ultima volta**, parte con radice verificata, `/var` persistente e nessun timer armato; si aggiorna dal PC di sviluppo senza chiavetta; un aggiornamento fatto fallire apposta lo riporta da solo alla versione precedente; con il certificato iscritto nel firmware parte con Secure Boot attivo; il rumore di fondo resta a zero.

## Cosa fa questo sotto-passo

Porta sulla macchina vera tutto ciò che i sotto-passi da P0.5a a P0.5e hanno costruito e provato in QEMU. Non aggiunge meccanismi nuovi, con due eccezioni, entrambe correzioni emerse dal registro della tua ultima costruzione:

1. **Servizi periodici di systemd disattivati.** Buildroot attiva ogni unità che un pacchetto porta con sé. Con gli strumenti di aggiornamento ne erano arrivate tre da non avere mai su una macchina che registra.
2. **Il certificato di Secure Boot viene copiato sul disco** all'installazione, così il menu del firmware lo trova senza la chiavetta inserita.

## Le unità disattivate

| Unità | Che cosa avrebbe fatto | Perché no |
| --- | --- | --- |
| `systemd-sysupdate.timer` | Cercare aggiornamenti da sola, ogni settimana e quindici minuti dopo l'avvio | dawOS si aggiorna solo a comando. |
| `systemd-sysupdate-reboot.timer` | **Riavviare la macchina ogni giorno alle 4:10** se è installata un'immagine più nuova di quella in uso | Succede dopo un aggiornamento non ancora avviato, e anche dopo un ritorno alla versione precedente. Un riavvio non richiesto, in uno studio, non è accettabile. |
| `systemd-boot-update.service` | Copiare il boot loader dalla radice alla partizione di avvio quando è più nuovo | Quella copia **non è firmata**: con Secure Boot attivo, dopo un aggiornamento di systemd la macchina non sarebbe più partita. |
| `fstrim.timer`, `xfs_scrub_all.timer` | Manutenzione settimanale dei dischi | Sono raffiche di operazioni su disco in un momento scelto dalla macchina. Decisione aperta **D-25**: vedi sotto. |

Le prime tre erano difetti veri, e nessuna prova li avrebbe scoperti in tempo: la prima e la seconda scattano dopo ore o giorni, la terza solo al primo cambio di versione di systemd. Li ho visti leggendo il registro della tua costruzione. Per non dipendere dalla lettura dei registri, **il rapporto di avvio ha ora il campo `timers=`**: elenca ogni timer armato che non sia la pulizia giornaliera dei file temporanei, e tutte le prove pretendono `timers=none`. Un pacchetto che porta un timer con sé verrà notato alla prima `make qemu-test`.

Un dettaglio che ha richiesto un secondo tentativo: disattivare il timer non bastava, perché il servizio corrispondente lo riattiva attraverso una riga `Also=`. Vanno disattivati entrambi.

### Decisione aperta D-25: manutenzione periodica dei dischi

Il TRIM settimanale mantiene le prestazioni degli SSD; la verifica periodica di XFS scopre in anticipo i settori che si stanno rovinando. Sono utili, ma vanno fatti in un momento scelto: allo spegnimento, o a comando da un'interfaccia di manutenzione. **Deciso il 15 novembre 2026, d'accordo con l'utente: restano spenti per tutta la Fase 0**; il momento in cui farli si decide quando si definiranno i servizi di sistema. Per qualche mese un SSD NVMe non ne risente.

## Prima di cominciare

- **Le chiavi.** `keys/` sul PC di sviluppo contiene ora tre cose da non perdere: la chiave dell'host SSH, la chiave di Secure Boot e la chiave degli aggiornamenti. Fanne una copia fuori dal PC **prima** di installare: da questo momento una macchina dipende da loro.
- **Le misure.** L'installazione cancella la partizione `state`. I risultati del passo P0.4b sono già nel repository; se sul 285K c'è altro da tenere, copialo ora con `make measure-fetch HOST=INDIRIZZO`.
- **Il monitor** resta sull'uscita HDMI della scheda madre.
- **Secure Boot** resta spento (_Other OS_) fino al punto 6.

Negli esempi `INDIRIZZO` è l'indirizzo del 285K. Per digitare la passphrase della chiave SSH una volta sola:

```bash
eval "$(ssh-agent -s)" && ssh-add
```

## Comandi

### 1. PC di sviluppo: costruire e scrivere la chiavetta

```bash
cd ~/daw-os && git pull
```

```bash
make image
```

```bash
make qemu-test
```

Atteso, con il campo nuovo:

```text
DAWOS-BOOT-REPORT … rootpart=dawos-root-0.0.1.<data e ora> timers=none var=state failed_units=0 …
PASS: boot report matches: failed_units=0 realtime=1 secureboot=1 verity=1 timers=none var=state
```

```bash
cat output/images/version.txt
```

Annota la versione: è quella che finirà sul disco.

```bash
cp output/images/installer.img /mnt/c/Users/<utente-windows>/Downloads/
```

Scrivi la chiavetta con balenaEtcher.

### 2. 285K: installare

Avvia dalla chiavetta (F8 all'accensione). Il menu mostra due voci, quella normale e quella «verbose»: scegli la normale. Dal PC di sviluppo:

```bash
ssh root@INDIRIZZO
```

Sul 285K:

```bash
dawos-install --list
```

```bash
dawos-install --model 'MODELLO' --serial 'NUMERO-DI-SERIE'
```

L'anteprima mostra ora, tra le altre, le partizioni `dawos-root-<versione>` e `dawos-verity-<versione>`, e in fondo la riga di comando con la tabella di dm-verity.

```bash
dawos-install --model 'MODELLO' --serial 'NUMERO-DI-SERIE' --write
```

Dopo la formattazione compaiono due righe nuove rispetto al passo P0.4a:

```text
Verifying the root partition on the disk...
Installing the boot loader and the unified kernel image...
```

```bash
poweroff
```

Togli la chiavetta e riaccendi.

### 3. Primo avvio, Secure Boot ancora spento

Dal PC di sviluppo:

```bash
make remote-test HOST=INDIRIZZO SECUREBOOT=0
```

Atteso:

```text
DAWOS-BOOT-REPORT version=0.0.1.<data e ora> … secureboot=0 verity=1 rootpart=dawos-root-0.0.1.<data e ora> timers=none var=state failed_units=0 …
PASS: INDIRIZZO matches: failed_units=0 realtime=1 secureboot=0 verity=1 timers=none var=state
```

Poi lo stato delle immagini e alcuni controlli:

```bash
ssh root@INDIRIZZO 'dawos-update --status; dmsetup status dawos-root; grep " /var " /proc/mounts; systemd-analyze; journalctl -b -p warning --no-pager | tail -n 20'
```

Atteso: un'immagine `(good)`, senza contatore; `0 <settori> verity V`; `/var` su una partizione `ext4`; il tempo di avvio.

### 4. Primo aggiornamento senza chiavetta

Sul PC di sviluppo, una costruzione nuova:

```bash
make image && cat output/images/version.txt
```

```bash
make remote-update HOST=INDIRIZZO REBOOT=1
```

L'uscita mostra lo scaricamento attraverso il tunnel, la firma (`gpg: Good signature`), la scrittura nello slot libero e l'elenco delle immagini, con la nuova `(under assessment)`. Dopo un minuto:

```bash
make remote-test HOST=INDIRIZZO SECUREBOOT=0
```

Atteso: `version=` e `rootpart=` con la versione nuova.

```bash
ssh root@INDIRIZZO dawos-update --status
```

Atteso: due immagini, entrambe `(good)`.

### 5. Ritorno automatico

Una terza costruzione, che verrà fatta fallire:

```bash
make image
```

```bash
ssh root@INDIRIZZO "mkdir -p /var/lib/dawos/test && echo dawos-root-$(cat output/images/version.txt) > /var/lib/dawos/test/fail-boot-on"
```

```bash
make remote-update HOST=INDIRIZZO REBOOT=1
```

La macchina proverà tre volte l'immagine nuova, riavviandosi da sola, e poi tornerà alla precedente. Lascia passare **tre minuti** (ogni tentativo comprende l'avvio del firmware), poi:

```bash
make remote-test HOST=INDIRIZZO SECUREBOOT=0
```

Atteso: `rootpart=` con la versione del punto 4, **non** l'ultima.

```bash
ssh root@INDIRIZZO 'dawos-update --status; rm -f /var/lib/dawos/test/fail-boot-on; journalctl --list-boots --no-pager | tail -n 6'
```

Atteso: l'immagine del punto 4 `(good)`, l'ultima `(failed: no boot attempts left)`, e tre avvii brevi nell'elenco.

### 6. Secure Boot

Finora la macchina ha avviato immagini firmate senza controllarne la firma. Ora si iscrive il certificato e si accende il controllo. I nomi delle voci li cito a memoria per le schede ASUS: **vanno cercati sulla scheda**, e una foto di ogni pagina mi aiuta a correggere la guida.

Entra nel firmware dal sistema:

```bash
ssh root@INDIRIZZO systemctl reboot --firmware-setup
```

Nel firmware, in modalità avanzata (F7):

1. _Boot_ → _Secure Boot_ → _Key Management_.
2. Voce dell'archivio delle firme, _DB Management_ (o _Authorized Signatures_) → **_Append_** (aggiungere). **Non** _Set New_ né _Delete_: sostituirebbero o toglierebbero le chiavi esistenti.
3. Alla domanda se caricare le chiavi di fabbrica: **No**. Scegli il file dal disco interno: `dawos` → `secure-boot` → `dawos-dev-secure-boot.cer`.
4. Tipo di file: _Public Key Certificate_. Conferma.
5. Torna a _Secure Boot_ e imposta _OS Type_ su _Windows UEFI mode_: su ASUS è la voce che accende Secure Boot.
6. Salva ed esci (F10).

Se il file non comparisse sul disco interno, è anche sulla chiavetta d'installazione, nello stesso percorso.

Dal PC di sviluppo:

```bash
make remote-test HOST=INDIRIZZO
```

Atteso: `secureboot=1`.

```bash
ssh root@INDIRIZZO 'bootctl status 2>/dev/null | sed -n 1,8p; dmesg | grep -i "secure boot"'
```

**Se la macchina non parte** e il firmware mostra un avviso di violazione di Secure Boot: rientra nel firmware (Canc all'accensione), rimetti _OS Type_ su _Other OS_, salva. La macchina riparte come al punto 5, e mi dici che cosa hai visto.

### 7. Il rumore di fondo è ancora a zero?

Il firmware è cambiato (Secure Boot) e l'immagine anche. Quindici minuti di misura confermano che nulla ha introdotto interruzioni di gestione del sistema. Gli strumenti ora sono nell'immagine e i risultati sul disco: non serve più `make measure-prepare`.

```bash
ssh root@INDIRIZZO dawos-hwnoise 15m secureboot
```

Dopo sedici minuti:

```bash
ssh root@INDIRIZZO dawos-hwnoise --status
```

Atteso: `verdict: PASS` e `thermal: ok`, come nella misura `tuned` del passo P0.4b.

```bash
make measure-fetch HOST=INDIRIZZO
```

```bash
ssh root@INDIRIZZO dawos-topology > docs/misure/fase-0/topologia-285k.txt
```

```bash
git add docs/misure && git commit -m "Phase 0 measurements: hardware noise with Secure Boot, topology after P0.5" && git push
```

## Da verificare sul 285K

Sono le incognite di questo sotto-passo: se una di queste non regge, ci si ferma lì.

| Punto | Che cosa potrebbe andare diversamente | Dove si vede |
| --- | --- | --- |
| Partizioni trovate per nome dietro il controller VMD | Il kernel non costruisce la radice verificata e resta in attesa | Punto 3: nessun avvio. La voce «verbose» della chiavetta non aiuta sul disco: fotografa lo schermo. |
| Identità della macchina dal firmware | — | Già verificato: l'identificativo è valido. |
| Il firmware lascia rinominare i file della partizione di avvio | Il contatore dei tentativi non scende, o l'immagine non viene confermata | Punti 3 e 5: `dawos-update --status`. |
| Il tunnel SSH attraverso WSL2 | `make remote-update` non riesce a scaricare | Punto 4. |
| Tempo dei tre tentativi | Più di tre minuti | Punto 5: basta aspettare ancora. |
| Menu di Secure Boot del firmware ASUS | Nomi e passaggi diversi da quelli che ricordo | Punto 6. |
| Secure Boot e rumore di fondo | SMI comparsi dopo l'attivazione | Punto 7. |

## Limiti noti di questo sotto-passo

- La prova di manomissione non si ripete sul 285K: alterare apposta il disco di una macchina vera per vederla fermarsi non aggiunge nulla a ciò che le prove in QEMU dimostrano, e costa una reinstallazione.
- Sul 285K restano valide anche le chiavi di Secure Boot già presenti nel firmware (ADR 0015).
- Il contenitore da rack (D-22) non c'è ancora: le misure termiche andranno rifatte lì.
